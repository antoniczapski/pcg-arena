## Grammatical Evolution (GE) Generator  
URL: `https://www.um.edu.mt/library/oar/bitstream/123456789/22937/1/Evolving_Levels_for_Super_Mario_Bros_Using_Grammat.pdf`  
**Summary:** This generator uses **search-based PCG** with an explicit grammar. Levels are encoded as sequences of grammar rules (design grammar productions) which expand into complete tile maps. A **genetic algorithm** evolves populations of these sequences. The fitness function rewards placing many game elements (enemies, blocks, pipes, etc.) while minimizing invalid placements (conflicts or impossible layouts). Over generations, the generator learns sequences of grammar applications that tend to produce playable Mario levels. This approach was described by Shaker et al. (2012), who showed that grammatical evolution can rediscover patterns of the original levels【6†L1-L4】.  
**Thesis context:** Cite this as a classic **search-based (evolutionary)** PCG method. It illustrates grammar-based representation (like an L-system or shape grammar). You can reference Shaker et al. when discussing *search-based level evolution* or explaining your “Grammatical Evolution” seed. It also shows how fitness can combine playability heuristics with aesthetic criteria, informing your own generator evaluations.

## Hopper Level Generator  
URL: `https://julian.togelius.com/Shaker2011The.pdf`  
**Summary:** The *Hopper* generator is a **constructive, probabilistic** level builder introduced in the 2010 Mario AI Championship. It builds levels left-to-right, placing sections according to tunable probability tables. Key features: it alternates between auto-generated segments and snippets of hand-crafted level (to ensure playability), and it supports **adaptivity**: if a player fails a section too often, the algorithm can adjust probabilities to make future segments easier (e.g. reducing gaps or enemy density). Shaker et al. (2011) describe it as a hybrid design for competition levels. It is efficient and ensures all levels are technically completable by design.  
**Thesis context:** Use *Hopper* as an example of a **constructive generator with adaptivity**. When contrasting blind random generation vs. guided methods, cite Hopper’s use in Mario AI Championship as a case where a simple generator yields varied but balanced levels. This can justify design choices about using pre-designed “chunks” or dynamic difficulty adjustment in your generators.

## Notch (Infinite Mario Bros) Generator  
URL: `https://github.com/amidos2006/Mario-AI-Framework`  
**Summary:** This is the *default* Infinite Mario Bros generator (from Markus “Notch” Persson’s original implementation). Like Hopper, it is a **constructive, probabilistic** left-to-right generator, using fixed probability distributions to place tiles, enemies, and gaps. It includes basic playability checks (for example, ensuring no impossible jumps by chance). Because it lacks adaptability, it serves as a baseline: levels can be very easy or very hard by accident. It is the generator embedded in the Mario AI Framework reference implementation.  
**Thesis context:** The Notch generator is your **baseline** “familiar” level generator. You should cite it when explaining that PCG Arena includes a known standard. When discussing fairness and perception, note that players often perceive “Notch” levels as a known baseline (and indeed, your results showed Notch doing moderately well). Cite the Mario AI Framework source to credit where this engine comes from.

## NotchParam Generator (Parameterized Notch)  
URL: `https://julian.togelius.com/Shaker2011Feature.pdf`  
**Summary:** This variant extends the Notch generator by exposing **parameters** that bias level features: for example, how many gaps to include, how large they are, frequency of enemies or power-ups, etc. In practice, these parameters were explored by Shaker et al. (2011) to control difficulty and style. The generator uses the same left-to-right construction as Notch, but the actual probabilities come from user-specified parameter settings. This allows generating whole families of levels (e.g. an “easy” mode with few gaps vs. a “hard” mode with many).  
**Thesis context:** This shows how simple PCG can be made controllable. You can cite this to explain how one might implement **difficulty sliders** or user-configurable content within the arena. It also provides a source for discussing “feature-based” level design. If your thesis includes experiments with parameter-tweaking, reference Shaker et al. (2011) for this parameterized approach.

## NotchParamRand Generator (Randomized Parameterized Notch)  
URL: `https://julian.togelius.com/Shaker2011Feature.pdf`  
**Summary:** This variant uses the same parameterized Notch engine, but instead of a fixed setting, it **randomly chooses a parameter configuration** for each generated level. In other words, gaps, enemy counts, etc., are sampled from a predefined range. The idea (used in some experiments) is to introduce extra variety by randomizing difficulty knobs. It still produces all-completable levels but with wide-ranging styles.  
**Thesis context:** Mention this generator as a way to seed the arena with very diverse levels without extra algorithm complexity. It’s a straightforward way to produce random players’ experiences from the same base generator. When analyzing generator diversity and consistency, note that this approach can mimic having many different “sub-generators” in one by parameter randomization.

## Occupancy-Regulated Extension (ORE) Generator  
URL: `https://www.cs.hmc.edu/~pmawhorter/research/papers/procedural_level_generation_using_occupancy_regulated_extension-Mawhorter_Mateas-2010.pdf`  
**Summary:** ORE is a **chunk-based (case-based)** generator. It has a library of small hand-authored level segments (chunks with “anchor points”), and it assembles full levels by matching and connecting these chunks while regulating tile occupancy. For example, if certain tiles or enemy density exceed a threshold, ORE chooses a chunk with more open space next. This method, from Mawhorter & Mateas (2010), tends to produce long, horizontally sprawling levels with coherent local structure. It leverages human design (through the chunks) but arranges them algorithmically.  
**Thesis context:** Use ORE as an example of a **hybrid/assembly** approach: it contrasts with purely generative methods by reusing human patterns. Cite Mawhorter & Mateas for the concept of occupancy-regulated assembly. In your results or background, you can mention that ORE levels were rated as high-quality (since it uses real Mario pieces), and it’s a good demonstration of how chunk-based PCG can mimic hand-designed content.

## Pattern-based Generator (Pattern Count Fitness)  
URL: `https://julian.togelius.com/Dahlskog2013Patterns.pdf`  
**Summary:** This generator encodes levels as sequences of 1-tile-wide slices (micro-patterns) taken directly from real SMB levels. It then uses an evolutionary search where the *fitness function* is “pattern count”: it counts how many occurrences of a set of larger pattern templates (meso-patterns) appear in the level. Patterns might be common structures like “three high blocks” or “staircases.” The count variant adds fitness for each occurrence, which tends to favor frequent repetition of popular patterns. It typically produces levels that reuse many original motifs but can result in repetitive designs.  
**Thesis context:** The pattern generator family is a clear example of **data-driven PCG** that directly reuses content. Cite Dahlskog & Togelius (2013/2014) as the origin of this approach. You can use it to illustrate the idea of a *fitness-as-pattern-match* criterion. In discussions of what makes levels “feel Mario-like,” these generators are key examples: their success (and failure) in the arena helps assess whether matching motifs alone yields fun levels.

## Pattern-based Generator (Pattern Occurrence Fitness)  
URL: `https://julian.togelius.com/Dahlskog2013Patterns.pdf`  
**Summary:** A variant of the above pattern-evolver, but with a different fitness: “pattern occurrence” counts each target pattern at most once. In other words, it rewards including as many *distinct* Mario-like patterns as possible rather than repeating the same ones. This encourages diversity of pattern usage. It still uses evolution and the same slice-based encoding. The result tends to be more varied levels (though sometimes patchy if it tries too many rare patterns).  
**Thesis context:** Use this as another example of **pattern-based search**. The difference in fitness highlights how a small change can promote or discourage repetition. When analyzing level variety or mentioning custom fitness functions, this generator demonstrates how you might prioritize diversity. Again, cite Dahlskog & Togelius for details on the pattern approach and how variants differ.

## Pattern-based Generator (Weighted Pattern Count Fitness)  
URL: `https://julian.togelius.com/Dahlskog2013Patterns.pdf`  
**Summary:** This third variant also builds on pattern-based evolution. Its fitness still counts pattern occurrences, but weights each pattern by its rarity (patterns that appear less frequently in original levels get higher weight). Thus, rare patterns (like a tricky multi-enemy jump) are considered more valuable. This encourages the generator to include some uncommon elements of Mario. Otherwise it’s implemented like the basic pattern count generator.  
**Thesis context:** This variant shows a nuanced fitness design. When discussing how to balance novelty vs. conformity, use this as an example of encoding “rarity awareness” in fitness. It also allows you to explain why some generators might produce very creative but occasionally nonsensical levels (if a pattern is rare because it’s usually hard). It’s instructive for the section on fitness engineering in search-based PCG.

## MarioGPT (Text2Level via GPT-2)  
URL: `https://openreview.net/attachment?id=dcA1jWmVX5&name=pdf`  
**Summary:** *MarioGPT* is a recent deep learning generator presented at NeurIPS 2023. It uses a pretrained GPT-2 language model (at character-level) fine-tuned on Mario level data. Crucially, it is *promptable*: a user can input a short text prompt (e.g. “a level with lots of coins”) and the model generates a complete level as text characters. It operates like an autoregressive model that outputively extends the prompt. The trained model learned the implicit “grammar” of Mario levels from examples, allowing natural-language control of content. The reference implementation by Sudhakaran et al. includes code for generation and conditional sampling.  
**Thesis context:** This generator is a prime example of **PCG via large neural models**. Cite the MarioGPT paper to discuss modern ML approaches to level design, especially if you use natural language. It stands in contrast to rule-based PCG; you might analyze its output diversity or how well players liked it. It also justifies exploring text-conditioned PCG and ties into your Mario-DPO training (since you fine-tune a GPT-2 as well).

## MarioGAN (DCGAN + CMA-ES Latent-Space)  
URL: `https://dl.acm.org/doi/10.1145/3205455.3205517`  
**Summary:** This generator comes from Volz et al. (GECCO 2018). It first trains a **Deep Convolutional GAN** (DCGAN) on real SMB level segments (from Video Game Level Corpus). The GAN’s generator network can produce new segments by sampling latent vectors. To create full levels, one can tile segments or directly search the latent space. The method uses **CMA-ES** (an evolutionary algorithm) to find latent vectors that optimize a chosen fitness (e.g., matching a target tile distribution or maximizing enemy count). Thus it blends generative ML (GAN) with search. A pretrained model and code are available in the DagstuhlGAN repository.  
**Thesis context:** Use MarioGAN to exemplify **latent-space PCG**. It shows how GANs can capture style and then be steered by optimization. In discussing learned generators, mention that MarioGAN was one of the first neural-level generators and still yields reasonably good levels. Also note the use of external optimization (CMA-ES) to tweak outputs, which parallels reward-guided generation in your Mario-DPO.

## MarioDiffusion (Text-to-Level Diffusion)  
URL: `https://arxiv.org/abs/2507.00184`  
**Summary:** This is a state-of-the-art generator introduced at AIIDE 2025. It uses **diffusion models**, a modern generative technique, to create Mario level segments. Specifically, it conditions a diffusion model on textual captions describing the scene (“flat ground with two pipes and many coins”). The model learns to generate corresponding tile maps (frames of 7–8 columns). Because it is text-conditioned, users can influence content via natural language (like MarioGPT, but using diffusion instead of a transformer). Pretrained weights and generation code are provided by Schrum et al. The approach tends to create coherent, high-quality tiles that align with the prompt.  
**Thesis context:** This generator represents the latest “neural, text-to-level” approach. Cite this to discuss how PCG is moving into multimodal generative AI. If you use (or plan to use) such models, it’s a direct parallel. It also highlights that player feedback in PCG Arena (which is also in natural language tags) is conceptually similar to how a model like MarioDiffusion uses text guidance.
